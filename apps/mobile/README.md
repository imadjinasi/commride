# CommRide Mobile

Flutter application for the first-Club CommRide pilot.

## Current scope and evidence

Repository source covers Home / Ride / Explore / Clubs / Profile navigation,
Firebase Email/Password authentication, Rider profile and Vehicle onboarding,
Club/Ride lifecycle, Route Planner, Briefing / Ready, Active Ride location sharing,
Live Group, Quick Actions, Checkpoints, private Comms, SOS, notifications and Recap.
Explore/social placeholders do not imply a public feed/follow/badge implementation.

PR #68 replaces the embedded Google Maps SDK with `maplibre_gl` and the backend
provider with Geoapify. Google Maps billing/native keys are no longer required.
The migration does not prove actual provider requests, installed-device rendering,
Firebase integration, background GPS, push delivery, signing or field acceptance.

Current provider behavior, limits and acceptance are defined in
[MapLibre + Geoapify pilot migration](../../docs/deployment/maplibre-geoapify-pilot.md).
Exact-head CI evidence is recorded in the PR; do not reuse a previous source
baseline's PASS as evidence for new changes.

## Toolchain and first bootstrap

Use the Flutter version pinned by `.github/workflows/mobile-ci.yml`, a compatible
Android SDK and Java 21. iOS builds require Xcode on macOS and a separately
accepted Bundle ID/provider registration.

Native directories are generated by a real Flutter SDK, not hand-fabricated.
From `apps/mobile`, before adding any local provider/signing files:

```bash
flutter create --platforms=android,ios --project-name commride_mobile --org io.github.imadjinasi .
python tool/configure_platforms.py
python tool/verify_platforms.py
flutter pub get
flutter analyze
flutter test
```

The configurator sets the accepted Android application ID
`io.github.imadjinasi.commride`; it does not finalize an iOS identity. The Android
namespace may retain the generated Dart project name; application ID is the
Firebase/signing/distribution identity.

The clean-source verifier must run before real Firebase/signing files are placed
in native directories. A missing Python executable is a local tooling limitation,
not evidence that native declarations passed or failed.

## Firebase configuration

The operator already created Firebase project `commride-pilot`, registered the
Android app and enabled Email/Password. Do not recreate those resources without
an evidenced mismatch.

Complete the official FlutterFire/native configuration locally. Keep
`android/app/google-services.json`, `ios/Runner/GoogleService-Info.plist`, generated
`lib/firebase_options.dart`, service-account files and signing material out of Git.
The app currently uses `Firebase.initializeApp()` with native configuration; do
not assume generating an unused options file alone completes integration.

Authentication flow:

1. Firebase determines signed-in/out state; signed-out users see Sign In / Create Account.
2. Signed-in users call `GET /v1/me` with a Firebase ID token.
3. `404 rider_profile_not_found` enters profile onboarding.
4. `PUT /v1/me` creates/updates only the authenticated Rider's profile.
5. Completed onboarding enters the CommRide shell.

The client never supplies authoritative auth subject. Missing Firebase/API
configuration shows setup-required state instead of bypassing authentication.
No SMS OTP or extra login provider is required for this MVP.

## API and map configuration

Supported Dart defines:

- `COMMRIDE_ENV=development|production`
- `COMMRIDE_API_BASE_URL`: real reviewed Worker URL
- `COMMRIDE_MAPS_ENABLED=true|false`
- `COMMRIDE_MAP_STYLE_URL`: HTTPS Geoapify style URL with a dedicated client map key

Copy `pilot-defines.example.json` to ignored `pilot-defines.local.json`. Use a local
editor to set the actual Worker URL and client map style, rather than pasting keys
into chat, commands, screenshots or GitHub. The example intentionally disables
maps and uses `https://example.invalid`; it is not deployment configuration.

The accepted style URL shape is:

```text
https://maps.geoapify.com/v1/styles/osm-bright/style.json?apiKey=<CLIENT_MAP_KEY>
```

Never put the backend `GEOAPIFY_API_KEY` or FCM service-account credentials in this
file. Client keys are recoverable from an installed binary; separate keys do not
by themselves guarantee provider-side API or certificate restrictions.

After backend/provider/Firebase setup and real signing configuration:

```bash
flutter run --dart-define-from-file=pilot-defines.local.json
flutter build apk --release --dart-define-from-file=pilot-defines.local.json
flutter build appbundle --release --dart-define-from-file=pilot-defines.local.json
```

Verify the local JSON file remains ignored before staging anything. Do not use
`git add .` to collect provider setup files.

## Club / Ride lifecycle and planning

Club lists are membership-scoped. Owner/admin invitations, invitation acceptance,
Ride creation, Member/Sweeper/Navigator invitations and Leader lifecycle commands
use authenticated APIs, not authoritative state invented on the client.
Rider-ID invitation remains an internal baseline; public discovery and friendly
invitation links are separate future work.

Joined participants can view saved RoutePlans; Leaders edit Draft/Published plans.
The planner supports endpoint search, alternatives before Stops, Add Stop,
reorder/remove, recompute, Checkpoint type/planned duration and revision save.
A failed recomputation preserves the previous valid route and Stops.
Active Ride route replacement remains a later operational command, not a silent
rewrite of the pre-Ride plan.

Geoapify motorcycle mode is not a car fallback. Alternatives are recommended/
shortest candidates only when materially different. Search Along Route searches
up to six sampled 5 km areas; it can miss places between samples on long routes.
Results are geographic candidates, not confirmation of road access. Detour totals
remain unavailable/null until a Stop is added and routing is recomputed.

The planner remains a list/summary flow. The Live Group map is the embedded map
surface in this migration; this is not an unimplemented planner map canvas or
built-in turn-by-turn navigation claim. External navigation to the next Stop or
destination remains independent of the SDK/provider choice.

## Briefing and readiness

Leader publishes an immutable Briefing tied to a RoutePlan revision, with notes,
Leader/Sweeper context and expected/Ready counts. Each Rider acknowledges that
exact revision. Changed routes leave the old Briefing readable but stale; Ready
waits for a new Briefing and does not inherit acknowledgement from older versions.
Readiness is advisory, not a hard Start Ride blocker.

## Active Ride location and realtime

Authentication, onboarding, Club browsing, planning and opening the map do not
request location permission. The Rider explicitly starts tracking from an Active
Ride. Location permission, Ride state and transport state remain separate.

The Geolocator adapter preserves observation timestamps. Bounded offline buffering
keeps the newest pending position rather than a full GPS trace. A shared signed-in
runtime owns the Ride WebSocket, avoiding competing screen-specific sockets for
Live Group, Comms or SOS. Reconnect uses a fresh Firebase token in an Authorization
header, never a token in the URL. The IO client is Android/iOS-oriented, not an
implied browser transport implementation.

Android declarations include release INTERNET, coarse/fine location,
foreground-service/location-service and notification permissions. There is no
blanket `ACCESS_BACKGROUND_LOCATION` request. iOS declarations preserve location
explanations, location/remote-notification modes and the FlutterFire notification
delegate; they do not invent APNs signing entitlements.

End Ride / server `ride.ended` and sign-out tear down sharing. Lock-screen,
background, reconnect, OEM battery and force-stop behavior still need device
verification. Never claim reliable terminated-app tracking from CI.

## Live Group map and Quick Actions

MapLibre consumes server-accepted RiderPresence. One latest marker per Rider
retains name, role, Live/Stale/Offline state and observation age. Old observations
do not replace newer ones; elapsed time can demote Live to Stale, never promote
Stale/Offline without a fresh accepted observation. Ride end leaves last-known
positions explicitly Offline.

Native map writes are serialized and coalesced to the latest waiting snapshot.
The map does not start its own GPS stream or follow movement automatically.
Fit Group is explicit. Missing/invalid style configuration and initialization or
native-update failures keep the operational list accessible. Style initialization
has a finite timeout and a deliberate retry action. Successful style loading does
not prove all remote tiles loaded correctly; check actual-device behavior.
Provider/data attribution remains visible and linked.

Quick Actions are Saya Berhenti, Saya Tertinggal and Butuh Bantuan, with an optional
reason capped at 240 characters. The client sends no authoritative Rider identity
or second location claim. Server presence context may be absent. Disconnected
sends fail explicitly; there is no unbounded offline action queue. Butuh Bantuan
is not SOS or emergency-service dispatch.

## Checkpoints, Comms, SOS and Recap

Checkpoint arrival is a manual check-in, explicitly not GPS verification. The
Leader releases the current checkpoint; missing Riders require confirmation.
Completed history is read-only and mutations use authoritative API responses.

Comms history and sends are private, D1-authoritative and idempotent through the
same `clientMessageId` on retry. Leader announcements remain distinct from chat.
HTTP success does not depend on realtime delivery; history/refresh recovers gaps.
Completed Comms is read-only. No rich-text execution, attachments or voice notes.

SOS is a separate persisted incident with deliberate confirmation and a retry-safe
`clientCommandId`. No-GPS SOS remains valid; attached presence is trusted
last-known context, not a promise of current location. Raising Rider can cancel;
Leader can resolve. Active SOS blocks End Ride. CommRide does not automatically
contact ambulance, police or public emergency services.

Recap distinguishes the planned route from sparse actual journey samples; absent
samples never become a fabricated exact GPS trail or actual distance.

## Notifications and acceptance

One app-owned notification controller checks existing permission without prompting
at startup. Profile offers explicit notification opt-in, token rotation is
synchronized, foreground messages are surfaced and sign-out attempts best-effort
token removal without blocking sign-out. Push is non-authoritative.

Real FCM/APNs delivery requires provider secrets/capabilities and actual devices.
CI runs formatting, analysis, tests, reproducible native declarations, Android
debug APK and release AAB build gates without real credentials. Those artifacts
are not Play-ready signing or installed-device acceptance.

Follow [pilot checklist](../../docs/pilot-release-checklist.md) and
[operator runbook](../../docs/deployment/pilot-operator-runbook.md): repository
checks, provider setup, two-Rider smoke, physical-device tests, then a safely
conducted three-vehicle convoy. Do not close device/field issues on CI alone.
